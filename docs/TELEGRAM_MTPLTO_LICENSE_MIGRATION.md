# Telegram MTProto license migration

Status: **PREPARATION ONLY — runtime migration is not implemented or tested in this branch yet.**

## Why this work exists

The current `core/package-lock.json` resolves:

- `telegram@2.26.22` (GramJS package, MIT)
- `@cryptography/aes@0.1.1` as a transitive dependency of `telegram`, declared `GPL-3.0-or-later`

The application imports the GramJS client in:

- `core/telegram.js`
- `core/telegram-login.js`

The login helper also imports `input`, which brings an old `inquirer` dependency chain. This is a dependency/license review finding, not a legal conclusion that the whole application is necessarily a GPL-covered derivative. Distribution counsel should review the actual linking/distribution model.

## Candidate evaluated

`teleproto@1.233.0` is the current npm version observed during preparation. Its npm metadata declares MIT and lists these runtime dependencies: `big-integer`, `buffer`, `cifrante`, `mime`, `node-localstorage`, and `socks`.

The teleproto documentation explicitly describes migration from GramJS and says that `StringSession` accepts existing GramJS session strings. It also warns that some generated API schema types and result shapes have changed. The `cifrante` source repository contains MIT SPDX headers in inspected source files, but its full packaged dependency/license graph still needs to be verified from the exact published tarball before approval.

References reviewed:

- https://www.npmjs.com/package/telegram
- https://www.npmjs.com/package/teleproto
- https://docs.teleproto.dev/
- https://github.com/sanyok12345/teleproto
- https://github.com/sanyok12345/cifrante

## Planned implementation

1. Pin `teleproto` to the reviewed version (do not use a floating range for the first migration).
2. Remove `telegram` and `input` from `core/package.json`.
3. Replace imports:
   - `telegram` → `teleproto`
   - `telegram/sessions` → `teleproto/sessions`
4. Replace `input.text()` prompts with Node.js `node:readline/promises`; close the readline interface in a `finally` block.
5. Regenerate `core/package-lock.json` using npm itself on Node.js 20+ with lifecycle scripts disabled during lock generation. Do not hand-edit the lockfile.
6. Verify the resolved production dependency graph contains no `@cryptography/aes` and no unapproved copyleft licenses. Generate an SPDX or CycloneDX SBOM and retain it as a CI artifact.
7. Add regression tests for session loading, connection, identity lookup, dialogs, message reads, text sends, photo sends, and safe cleanup. Tests must use mocks and must not require real Telegram credentials.
8. Run `npm ci`, `npm test`, and the license/SBOM gate in CI.
9. Perform a separate opt-in live smoke test using a dedicated Telegram test account. Never print or commit `TELEGRAM_SESSION`, API hashes, phone codes, or 2FA passwords.

## Acceptance gates

- [ ] Lockfile is regenerated by npm and is reproducible.
- [ ] `telegram`, `@cryptography/aes`, and `input` are absent from the production dependency graph.
- [ ] Existing GramJS session string loads successfully in a controlled test.
- [ ] Telegram client API regression tests pass.
- [ ] License scanner finds no unapproved license.
- [ ] SBOM is attached to CI evidence.
- [ ] Live Telegram smoke test passes with a dedicated test account.
- [ ] No session material or credentials appear in logs, artifacts, or Git history.

## Important constraints

This document is a preparation record, not evidence that the migration has shipped. Do not treat the candidate package's MIT top-level license as proof that every transitive dependency is cleared. Do not merge this branch or deploy it until all acceptance gates pass and the license review is approved.
